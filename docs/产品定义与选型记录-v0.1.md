## 2 需求起点

### 2.1 原始诉求

需要一个适合游戏玩家、适合日常 Windows 电脑副屏常驻的性能监控软件。要求视觉上"高颜值、酷炫"，但现有工具要么过于简陋，要么过于专业化。

### 2.2 现有方案为何不适用

| 方案 | 优点 | 不适用的原因 |
|---|---|---|
| TrafficMonitor | 轻量、免费、任务栏常驻、占用极低 | 信息维度太浅，只有数字没有趋势，表现力不足以支撑副屏 |
| Netdata / Grafana / Zabbix | 实时性极强、指标极其丰富、视觉效果出色 | 面向运维场景，概念模型是节点与仪表盘，与玩家关心的指标不对应；部署与维护成本远超个人使用所需 |
| MSI Afterburner + RTSS | 数据最全（自带内核驱动）、免费、游戏内 OSD | OSD 只在游戏运行期间显示，退出游戏即消失；界面为调试信息风格 |
| Rainmeter | 皮肤生态丰富、视觉自由度最高 | 本身不是监控软件，需自行搭配插件与皮肤，配置门槛高，稳定性与资源占用不佳 |

结论：市场在"极简数字显示"与"专业运维仪表盘"之间存在明显空档，即常驻副屏、开箱即用、视觉具备设计感的方案。

## 3 竞品格局与可守定位

真正需要正面对待的竞品不是上述任何一个单点工具，而是"Afterburner OSD + Rainmeter 皮肤"这一组合。该组合已经覆盖硬核玩家群体，在数据深度与生态规模上均无法正面竞争。

但该组合存在共同缺陷：都需要用户自行折腾，且默认观感不佳。Rainmeter 需要安装皮肤、修改配置、调整坐标，多数用户使用数日后放弃；Afterburner 的 OSD 视觉粗糙且仅限游戏内。

由此得出可守的定位：

> 装上就是成品，默认状态即可用；退出游戏后副屏依然是有信息量的画面。

该定位直接约束后续所有取舍：默认零配置、不暴露配置文件、首屏不堆叠可调参数。

## 4 路线选择：自研还是 fork

### 4.1 候选 fork 标的评估

| 标的 | 现状 | 评估结论 |
|---|---|---|
| Libre Hardware Monitor | C# / WinForms，维护活跃 | 数据层最完整，但界面停留在旧式 WinForms；改造其界面等同于重写，且需承担既有技术债。应作为库引用，不作为 fork 对象 |
| Sidebar Diagnostics | C# / WPF，2019 年后基本停更 | 产品形态最接近目标（常驻侧栏），但不支持温度读取，依赖陈旧，仅可作结构参考 |
| Open Hardware Monitor | 已停更多年 | 不予考虑 |
| CAPFrameX | C# / WPF，维护活跃 | 帧率测量专业，但定位是性能分析工具而非常驻 HUD，场景不匹配 |
| TrafficMonitor | C++ / MFC | 简洁正是其定位，无法支撑所需表现层 |
| Rainmeter | C++ 挂件引擎 | 非监控软件，且其生态规模不可复制 |

### 4.2 结论

不复刻产品，复刻数据层。

本项目的核心难点不在界面，而在传感器采集：CPU 温度、风扇转速、功耗在 Windows 上必须通过内核驱动读取，涉及驱动签名、蓝屏风险、杀软误报，而这一层已由 LibreHardwareMonitor 积累多年，直接以库形式引用是唯一理性选择。

若 fork 一个完整项目，将继承其技术债与停滞风险，同时放弃唯一可能形成差异的部分——表现层。若从零自行实现驱动，则成本与风险均不可接受。

### 4.3 三层架构与复用边界

| 层 | 内容 | 策略 |
|---|---|---|
| 数据源层 | GPU 温度与功耗、CPU 温度、系统指标、帧率 | 全部复用现成方案（LibreHardwareMonitor、PDH、PresentMon） |
| 采集层 | 定时轮询、快照聚合、环形缓冲 | 自研，但保持极薄 |
| 表现层 | 副屏 HUD 的排版、动效、配色、多屏适配 | 完全自研，这是产品本体 |

## 5 开源前提带来的两处权重变化

项目确定采用开源方式发布，该前提改变了两项判断。

### 5.1 许可证

自有代码采用 Apache-2.0。LibreHardwareMonitorLib 为 MPL-2.0，属文件级 copyleft：以库形式引用只需在文档中保留其许可声明，不影响自有代码的许可方式；若修改其源文件，被修改的文件须继续以 MPL-2.0 发布，项目其余部分不受影响。该组合与开源发布完全兼容。

### 5.2 贡献者池

开源项目的成败很大程度取决于可参与贡献的人群规模。此类软件最容易被社区贡献的部分是主题与视觉，而 HTML/CSS 的潜在贡献者数量比 Rust GUI 高一个数量级——设计师、前端工程师、愿意折腾的玩家均可参与。若采用 Rust 自绘方案，贡献门槛将抬升至"具备 Rust GUI 开发能力"，实质上关闭了这一增长路径。

## 6 技术栈

### 6.1 本机环境实测

| 项 | 实测结果 |
|---|---|
| .NET SDK | 8.0.100，可用 |
| NuGet 通道 | 可用。LibreHardwareMonitorLib 0.9.6 实际还原成功，耗时 9.88 秒 |
| WebView2 运行时 | 已安装（Evergreen 版本 157.0.4341.46） |
| Node / npm | v22.22.2 / 10.9.7，可用 |
| Rust 工具链 | 未安装（无 cargo） |
| pip 公共源 | 不可用，psutil 无法安装。此项排除了以第三方 Python 依赖为基础的方案 |

### 6.2 方案对比

| 方案 | 数据层 | 表现层 | 交付形态 | 判定 |
|---|---|---|---|---|
| 纯 WPF / XAML | 可直接引用 LibreHardwareMonitorLib | 图表、动效、渐变需手写控件模板，风格调整成本高 | 单 exe 自包含 | 可行，但视觉迭代成本最高 |
| Python + 浏览器全屏 | 温度需经 pythonnet 中转或依赖外部进程 | Canvas / SVG 上限最高，迭代最快 | PyInstaller 产物笨重，额外驻留浏览器进程 | 原型阶段最优，产品化不利 |
| Rust + Tauri | 无对等传感器库，需 sidecar 或自行 FFI | Web 上限高 | 体积 8–15 MB | 不采纳，理由见 6.5 |
| Rust + egui / Iced | 无对等传感器库 | 自绘自由度高 | 体积 8–12 MB | 以重建整个生态为代价，不采纳 |
| C# 宿主 + WebView2 | 直接引用，能力最完整 | Web 上限高，样式调整等于修改 CSS | 单 exe，WebView2 由系统提供 | 采纳 |

### 6.3 选型结论

采用 C# / .NET 8 + WPF 宿主 + WebView2 渲染 + LibreHardwareMonitorLib 采集的组合。

其本质是将数据层交给 .NET 生态中最成熟的实现，将表现层交给排版能力最强的技术。并非折中方案，而是各层均取该层最优解。

### 6.4 三个实现细节

前端不引入 HTTP 服务与构建链。WebView2 提供 `SetVirtualHostNameToFolderMapping`，可将本地目录映射为虚拟站点，前端即为纯 HTML / CSS / JS，修改后刷新生效。无 npm、无打包步骤、无开发服务器。

进程内通信取代网络通信。宿主每秒生成快照对象，序列化为 JSON，通过 `PostWebMessageAsJson` 直接投递前端。无 WebSocket、无端口占用、无防火墙问题。

托盘图标不引入第三方包。项目开启 `<UseWindowsForms>true</UseWindowsForms>`，直接使用 `System.Windows.Forms.NotifyIcon`。

### 6.5 关于 Rust 路线的具体判断

需区分两种理解。

若指 Tauri：其在 Windows 上同样以 WebView2 为渲染内核，并不比 WPF + WebView2 获得更多异形界面能力，反而失去 LibreHardwareMonitor 这一数据层。真实落地形态将退化为 Tauri 外壳加一个 .NET 或 Python 的 sidecar 进程读取传感器，等于同时维护两套运行时。

若指 egui / Iced：自绘能力确实更强，代价是从传感器、托盘、多屏管理到发布流程全部自行重建。

Rust 的真实优势应予承认：常驻内存更低、分发体积更小、自绘性能更好。但对本项目而言，这些优势不足以抵消数据层重建与贡献者池收缩两项代价。

## 7 异形界面的实际边界

WPF 本身具备完整的异形窗口能力（`WindowStyle=None` 配合 `AllowsTransparency` 与 `Path` 几何），可绘制切角、圆形表盘或任意轮廓。但 WPF 与 WebView2 组合下该能力受限：WebView2 作为 `HwndHost` 承载的独立子窗口，与依赖分层窗口的透明机制冲突（airspace 问题），表现为透明区域变黑或完全不渲染。

因此"异形"需按三类分别判断：

| 类别 | 典型形态 | 可行性 | 说明 |
|---|---|---|---|
| 一、窗口内异形视觉 | 无边框、圆角、切角卡片、自定义描边、仪表盘 | 完全可行 | 由 CSS 实现，成本最低，覆盖绝大多数诉求 |
| 二、悬浮穿透浮层 | 数据浮于游戏画面之上 | 纯 WPF 可行，WebView2 不可 | 分层窗口在 Windows 上会退化为软件渲染，4K 高刷下自绘反而更耗 CPU |
| 三、真异形窗口 | 任意轮廓的窗口外形 | 需自绘 | `SetWindowRgn` 仅支持 1-bit 裁剪，边缘有锯齿；平滑轮廓必须自绘 |

副屏监控的主流场景中，主窗口为铺满屏幕的矩形，所谓异形实际指第一类，WebView2 足以胜任。

对第二、三类需求，应对策略是将渲染层抽象为可替换接口：v1 提供 WebView2 实现（矩形窗口加窗口内异形视觉），若后续确需游戏内浮层，再以 SkiaSharp 自绘实现接入同一份数据快照。如此今日选型不锁定明日形态。

需注意，游戏内浮层是与 Afterburner 与 RTSS 的正面竞争，不应在 v1 阶段开启。

## 8 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 温度读取依赖内核驱动 | LibreHardwareMonitor 通过自带签名驱动读取，该类驱动（WinRing0 系）曾遭挖矿程序滥用，常被安全软件重点监控；Windows 11 内核隔离（HVCI）亦可能拦截 | 界面层面设计优雅降级：不可读时显示占位符并提供说明入口，不显示 0、不弹窗。功能层面将 CPU 温度设计为可选能力，GPU 指标作为核心 |
| 发布体积 | 框架依赖模式约 5 MB，但要求预装 .NET 8 Desktop Runtime；自包含单文件约 60–70 MB | 采用自包含发布。对玩家群体而言，减少一个安装步骤的价值高于节省 50 MB |
| 多屏与 DPI | 副屏常为不同分辨率与缩放比例，坐标写死会导致错位 | WPF 设置 PerMonitorV2 DPI 感知，窗口定位通过枚举显示器而非固定坐标 |
| 虚拟显示适配器 | 本机存在向日葵、ToDesk、GameViewer 三个虚拟显示适配器，直接枚举会列出多块"显卡" | 设备枚举阶段过滤虚拟适配器，仅保留物理 GPU |
| SmartScreen 拦截 | 未签名可执行文件首次运行会触发安全提示 | v1 接受该提示；后续可申请 SignPath 的开源项目免费签名 |
| 代码托管可达性 | 实测 github.com 主站不可达、raw.githubusercontent.com 不可达，api.github.com 可达，gitee.com 可达 | 见第 10 节 D4 |

### 技术上，我会怎么实现？

我认为完全没有必要从零开始开发硬件传感器读取驱动。

可以采用这样的架构：

Windows UI 层

WPF / WinUI 3 / WebView2

仪表盘 · 图表 · 动画 · 交互

Telemetry Service（数据服务层）

统一数据模型 · 采样 · 缓存 · 历史记录

HWiNFO

传感器数据

LibreHardwareMonitor

开源传感器库

GPU SDK

GPU 专项数据

底层数据源可插拔，统一输出标准化遥测数据

这样 UI 团队可以专注于产品体验，底层数据采集则复用成熟项目和厂商接口。

我个人最看好的是：把硬件监控软件从「工程师工具」变成「电脑的数字仪表盘」。

现在很多高端 PC 已经有非常漂亮的机箱、RGB 灯光、液晶水冷屏，但 Windows 桌面上的硬件监控体验却还停留在十几年前。

我觉得这中间确实有产品创新的空间。尤其是把实时监控、历史趋势、智能告警和漂亮的 UI 结合起来，可能会是一款很有吸引力的 Windows 工具。
